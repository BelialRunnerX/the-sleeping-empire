Saving and compatibility

Native development snapshot · Reviewed 18 November 2026

Native saves distinguish committed transactions, known failure and uncertain outcomes. This distinction is part of the mechanics, not just an implementation detail.

Version matters. This is an implementation reference, not a promise that every feature is in your installed build. Provisional adaptations and limitations are stated explicitly. Controls describe the documented native snapshot and may differ in the Windows GUI handoff.

Three outcomes

Committed means the command’s verified publication completed. NotCommitted means that transaction did not publish its candidate. Unknown means the outcome cannot safely be determined in the current session: gameplay and further saves stop until reload. No automatic retry should duplicate a reward.

Ordinary simulation is different

Machines, movement and many live interactions advance before an ordinary snapshot. A known failed ordinary save leaves that advanced live state in memory and the earlier disk snapshot intact. It does not roll the whole world back. Transactional crafting, gear changes and selected configuration commands have narrower private-publication boundaries.

Compatibility

Reading an old save in a current build does not promise that an old build can read every new save. Retired work v2, retired loot metadata, newer item IDs and life-derived health have explicit compatibility limits. Keep recoverable backups and use a compatible build.

Multiplayer boundary

Stable IDs and local exclusive ownership are foundations, not a completed network game. These source notes do not claim authenticated remote commands, actor ACLs, replication, anti-rollback protection or WAN duplicate suppression. Cross-network multiplayer remains a separate validation and implementation task.
